1 · AI agents with guardrails

An agent gets what the grant allows, and nothing else

A grant is a credential with limits, issued on the machine the agent will work on. That machine checks it on every command and every file operation, so nothing on the agent's side can widen it.

  1. Which features and paths

    Commands, files below given folders (read, or read and write), screenshots, the desktop, the clipboard, forwarding. Anything not listed is refused, including making itself a pairing that would outlive the grant.

  2. Which commands

    Only commands that start with an allowed program. Pipes, redirects and $ are refused, so a command cannot start another one.

  3. For how long

    The grant expires and its sessions end with it. remohop host revoke ends it early.

  4. With your approval

    each: you approve every command and file change; first: the first one of each session. A request nobody answers is refused after 30 seconds.

  5. On the record

    Every action goes into the host's audit log under the grant's name; with --record the output of commands and terminals is saved too.

Stop everything

remohop host panic

Suspends every grant and ends every agent session at once. It needs no window or hotkey and works from any terminal on the host, over SSH too.

The agent knows its limits

remohop_limits

The agent can ask what it may do, and every refusal names the limit and the grant. It is told to stay within them instead of looking for a way around.

What a grant does not do. A command allow-list is a guard rail, not a sandbox: an allowed program that can run others (make, git hooks, any interpreter) carries that power along, and approving ./deploy.sh approves whatever it does. Limits of the protection spells this out. For a whole team, RemoHop Teams issues the same grants from one policy and lets admins answer approvals.

2 · One tool instead of several

Remote desktop, terminal, files, tunnels and a mesh network, in one program

For you as much as for your agents. Use the desktop app, a browser, a phone or the command line; the machines on the other end run the same remohop.

direct · end-to-end encrypted

  • Remote desktopIn the desktop app or a browser: 2K and 4K, about 60 ms on a LAN, up to 144 fps, audio, several monitors.
  • Shell and background jobsTerminals that keep running after you disconnect, single commands, jobs with logs. PowerShell on Windows.
  • FilesCopy, sync and mount a remote folder; large transfers resume where they stopped.
  • Port forwarding and VPNTCP and UDP forwards like ssh -L and -R, Wake-on-LAN, and a VPN link into the host's network.
  • Mesh networkYour devices in one private network with names like nas.remohop. It works next to Tailscale and uses a shared tailnet as one more direct path.
  • Quick supportThe person you help double-clicks one program, reads you an ID and a password, and presses Allow for every connection.
  • Android and iOS appsControl your computers from a phone. An Android phone can be controlled too, an iPhone or iPad can share its screen.
  • One static binaryClient, host, rendezvous server, browser gateway and MCP server are one remohop for Linux, macOS and Windows.

3 · Trust you can check

End to end encrypted, direct by default, open source, and every server can be yours

The rendezvous server introduces the two machines by ID. After that the screen, keys, files and commands go over a direct QUIC connection that only the two ends can read. When no direct path exists, a relay forwards the same ciphertext.

  • QUIC with TLS 1.3, and CPace for the login. The password never crosses the network, and a man in the middle, the rendezvous server included, cannot complete the login.
  • Direct peer to peer by default. Hole punching and router port mapping first; a relay only if its operator turned it on and nothing else works.
  • The server sees ciphertext and metadata. Which IDs are online, their addresses and when they connect; never the content.
  • Every connection asks first. New devices come with a scam warning, and an allowed device only sees the screen until you tick more.
  • Open source under the AGPL-3.0.Source to be published under the AGPL-3.0. Run the rendezvous server, the relay and the browser gateway yourself, or connect on a LAN with no server at all.

Not done yet, stated plainly.

  • There has been no independent security audit.
  • The Windows downloads are not code-signed; SmartScreen warns. The macOS ones are signed and notarized.
  • Linux is the reference platform. macOS and Windows are covered by automated runs on hosted machines, not checked by a person on physical ones.
