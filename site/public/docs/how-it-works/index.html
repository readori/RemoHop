工作原理

网站上的工作原理页面用一张图讲清了这些内容：汇合服务器、各条连接路径及其尝试顺序、默认端口、六步连接流程和会话安全。本文是详细说明。

 控制端                                              被控机
+--------------------------+   UDP 打洞 + QUIC         +--------------------------+
| remohop <ID> shell ...   |<=========================>| remohop host             |
| remohop web、remohop mcp |   端到端加密              |  shell、文件、VPN、      |
+----------+---------------+                           |  桌面等                  |
           |                                           +------------+-------------+
           |  信令：谁在哪里                                        |
           +------------------>  remohop signal  <------------------+
                          （可选中继，默认关闭）
  • 被控机向汇合服务器注册，并获得自己的 ID。
  • 客户端向汇合服务器查询被控机。服务器把双方的候选地址互相告知。
  • 双方向对方的候选地址发送探测包，在各自的 NAT 上打洞，客户端通过第一条有应答的路径建立 QUIC 连接。如果双方的 NAT 看起来都能打通但第一次失败，客户端会换一个新的套接字再试一次。
  • 对称型 NAT 给每个目的地址分配一个新的公网端口，对方无法知道探测包会从哪个端口发出；只接受自己发过包的端口回包的 NAT（端口受限型）会丢弃这些包。不过很多对称型 NAT（常见于家用路由器和运营商网络，在中国尤其多）是按顺序分配端口的。连接汇合服务器时，每一端都能看到自己的 NAT 连续分配的两个端口。如果两者相差很小（1 到 16），它就把对后续端口的预测随候选地址一起发给对方；对方如果是锥型 NAT，就在服务器看到的对称型一端的地址上额外探测 48 个预测端口。这样的组合因此可以直连，而不必走中继。运行了一段时间的被控机会在应答前重新测量一次。双方都是对称型 NAT，或者随机分配端口的对称型 NAT 对上端口受限型 NAT，仍然无法打洞。这一机制不需要改动汇合服务器，旧版本的对端会忽略预测。
  • 被控机还会请求路由器转发它的 UDP 端口（PCP、NAT-PMP 或 UPnP，看路由器支持哪一种）。路由器同意时，转发得到的公网地址会成为又一个候选地址，无论客户端在哪种 NAT 之后都能连上，所以即使双方都是对称型 NAT 也能直连，而不必走中继。在被控机上用 remohop config portmap off 或 REMOHOP_PORTMAP=0 可以关闭；详见 security.md。
  • 两端在这条连接上运行基于密码的认证密钥交换。中间人（包括汇合服务器）无法完成这一交换。
  • 路径建立之后（或者确定连不上时），客户端会告诉汇合服务器这次走的是哪种路径（局域网、直连、打洞、路由器端口映射、端口预测、中继、WebSocket 桥接，或者失败）、从发出连接请求起用了多久，以及双方的 NAT 类型；走中继的会话之后换到直连时，还会再报告一次。报告不含 ID、地址或密钥，在后台经由客户端与服务器之间现有的连接发送，服务器只按月计数。不支持这种报告的旧服务器不会再被询问。在客户端用 remohop config outcomes off 或 REMOHOP_OUTCOMES=0 可以关闭。手机应用不发送这种报告。

中继

默认只走点对点直连；除非汇合服务器的运营者主动开启，否则不存在其他路径：

  • 只有运营者用 remohop signal --relay 启动服务器时才有中继。它默认关闭，因为这是唯一会真正消耗服务器带宽的功能。
  • 只有打洞失败之后才会使用，例如双方都在对称型 NAT 之后；或者一方只能通过 websocket 桥访问服务器时直接使用（见下文）。
  • 中继承载的仍是同一条端到端加密、经过认证的会话。中继只转发密文，无法读取内容，也无法加入会话。
  • 建立中继时会在 stderr 上提示，remohop <ID> ping 和 remohop status 中显示为 relayed。它更慢，并受带宽上限约束（--relay-kbps，每个会话默认 8000；--relay-total-kbps，默认 40000；--relay-max）。超过上限的流量会被整形（最多排队 100 毫秒，之后才丢弃），而不是直接截断，QUIC 的拥塞控制可以平滑地跟上。中继每 10 Mbit/s 大约消耗 1% 的 CPU 核。
  • 客户端或被控机可以用 remohop config relay off 或 REMOHOP_RELAY=0 拒绝中继。对某台被控机打洞失败之后，10 分钟内从同样的网络发起的后续命令会立即建立中继（打洞仍在同时进行，若直连路径有应答则直连胜出）。
  • 走了中继的会话不会无谓地一直走中继。会话存续期间，客户端会在后台继续尝试打洞：会话建立 5 秒后一次，之后再隔 20 秒、60 秒各一次，此后每 3 分钟一次；网络发生变化时也会立即尝试。每次尝试都向汇合服务器申请一次新的介绍（与新建连接时的请求相同），并从会话自己的套接字打洞。一旦某条路径有应答，会话的 QUIC 连接就迁移过去（QUIC 连接迁移：客户端先验证新路径，再切换；被控机自动跟随）。数据流、远程桌面画面和文件传输都不会中断，不需要重新登录，也不会再次询问被控机的主人。几秒后中继会被释放。双方都会记录日志 relayed session moved to a direct path after …，网页客户端、remohop status 和桌面应用中显示的路径会从 relayed 变为 punched（或 direct、lan）。新路径在会话自身的加密之内验证，因此只有会话已认证的那台被控机才能在其上应答；详见 security.md。这一机制不需要两端或汇合服务器的任何新功能，所以对旧版本的服务器和被控机同样有效。在客户端设置 REMOHOP_RELAY_UPGRADE=0 可以让走中继的会话一直留在中继上。经由 WebSocket 桥接的会话仍然走中继。

纯 IPv6 网络（NAT64）

有些网络只给设备分配 IPv6，通过 NAT64 和 DNS64 访问 IPv4 互联网，例如部分移动运营商，以及 Apple 审核 iOS 应用时用的网络。在这种网络里主机名照常可用（DNS64 返回一个由 NAT64 转换的 IPv6 地址），IPv4 地址却不行，而 RemoHop 经常遇到 IPv4 地址：用户输入的地址（203.0.113.7:21118）、按地址配置的汇合服务器，以及汇合服务器下发的被控机和中继地址。

  • 在 iOS 上（或设置了 REMOHOP_NAT64=on 的任何平台），如果因为没有 IPv4 路由而发不出发往 IPv4 地址的数据报，客户端就按标准方法找出网络的 NAT64 前缀（RFC 7050：向系统解析器查询 ipv4only.arpa 的 IPv6 地址），改发到内嵌该 IPv4 地址的 IPv6 地址（RFC 6052，支持所有前缀长度）。来自这个地址的回包被当作来自原 IPv4 地址，所以打洞、中继和 QUIC 会话都无需改动。前缀缓存 10 分钟；如果之后发往转换地址时发现没有 IPv6 路由，就退回 IPv4，下次重新查询前缀。
  • 在 IPv4 可用的网络里一切照旧：不查询，也不转换。Android 系统自带转换（464XLAT），不需要这一机制；桌面端和被控机可以用 REMOHOP_NAT64=on 打开（代价是失去 QUIC 在 Linux 上使用的批量 UDP 收发）。
  • 局限：DNS64 没有公布的 NAT64（ipv4only.arpa 没有合成地址）找不到；只转换 RemoHop 自己的 UDP 流量（websocket 网桥按主机名连接）。经过转换的路径就是一个普通的 NAT，打洞的效果与运营商级 NAT 相同。
