平台支持

状态与限制

  • NAT 穿透可能失败。 双方都是对称型 NAT，或一方是随机分配端口的对称型、另一方是端口受限型时无法打洞；没有中继可用时，连接会在几秒内失败并给出诊断信息。按顺序分配端口的对称型 NAT 会被预测，通常可以连上（见工作原理）。对于会记录未请求入站包的 NAT，Linux 被控机在 IPv4 上用低 TTL 预热包来应对。
  • IPv6 路径和真实的家用路由器未经测试。 NAT 测试使用的是 Linux 网络命名空间。
  • 远程桌面。 在一台只有 CPU 的 4 核虚拟机上，于浏览器中测得的端到端延迟：H.264 约 20 ms（720p）和 31 ms（1080p），软件 AV1 分别约 50 ms 和 61 到 227 ms。硬件编码器优先使用。其中 VideoToolbox（macOS）已验证：在 GitHub 托管的 Apple Silicon macOS 虚拟机（单显示器，1024x768，缩放 1）上，被控端会选用它，解码出的画面、指针和点击输入、只读模式以及两个观看者同时观看都在那里检查过，macOS 上的 libx264 和 SVT-AV1 也是如此。Retina 和多显示器的 Mac、macOS 上的锁屏控制以及实体 Mac 没有测试。NVENC、QSV、VAAPI、AMF 和 Media Foundation 未经测试；4K 60 fps 没有测试过。强制或选用软件 AV1 时，SVT-AV1 2.2 到 3.0 的实时预设有一个上游缺陷（屏幕上的小改动要到下一个关键帧才显示），在这些主机上 RemoHop 改用 libaom 并给出说明。在 X11 被控机上，输入屏蔽和隐私黑屏会报告为不支持。不支持原生 Wayland 采集。
  • 串口用伪终端和 picocom 验证过，没有真实的 UART 可用。USB/IP 已在托管运行器上用真实内核（dummy_hcd 虚拟 U 盘）验证，没有在实体 USB 设备上测试过。
  • 浏览器客户端在无头 Chromium 中对接真实的被控端验证过。
  • shell 会话在客户端断开后会保留一段时间。被控端重启后会话不会保留。
  • 打包与发布。 packaging/ 中有 nfpm 配置（.deb、.rpm、.apk）、安装脚本、systemd 单元、launchd 模板、汇合服务器的 Dockerfile，以及 Homebrew、Scoop、winget、AUR 和 Nix 的模板。发布版本由推送 v* 标签触发的发布工作流发布到 GitHub Releases；macOS 二进制和 RemoHop.app 已签名并经过公证，Windows 二进制未签名。让被控端开机自启的受支持方式是 remohop service install。
  • 手机作为被控端。 Android 手机可以被观看，经主人同意并开启无障碍服务后还能被控制（见移动端应用）。从屏幕采集到观看端的链路在 CI 中用模拟编码器和真实客户端测试，应用的被控模式在模拟器上测试到批准对话框为止；真机上的屏幕采集和控制尚未测试。iPhone 或 iPad 可以共享屏幕，只能观看（见移动端应用）：iOS 不允许任何应用控制设备。
  • 未在真实硬件上测试： 实体 Mac 上的一切（macOS 的 VPN 客户端、桌面被控端和输入只在托管虚拟机上验证过）、Windows 的 WebDAV 挂载、真实内核上的 USB/IP、除该虚拟机中的 VideoToolbox 以外的 GPU 编码器。手机应用每次改动都在 CI 中测试（iOS 应用在模拟器中，Android 应用在模拟器上）。
  • 账号由汇合服务器托管，需要运营者开启；服务器可以对设备隐瞒最新的日志条目，见 security.md。
  • 许可证： AGPL-3.0，另提供商业授权，见许可证。
