How it works: P2P hole punching and end-to-end encryption

How RemoHop connects two devices directly: what the rendezvous server does, the four connection paths, the default ports, the six steps of a connection, and why only the two ends can read a session. For the details, see the How it works guide and the security model.

In short: the host and the controller first talk to the RemoHop rendezvous server (remohop signal) for ID registration, presence, NAT type detection and the exchange of candidate addresses. Then both send UDP probes to each other at the same time to punch through their NATs, and set up a direct QUIC connection on the first path that answers, end-to-end encrypted with TLS 1.3 + CPace password authentication (bound to the Ed25519 identity keys). Remote desktop, terminal, files and every other feature are multiplexed over that one session. If punching fails, the connection switches to the (optional) relay within about 1.5 seconds, and the relay only forwards ciphertext.

What the session carries (never via the server)

  • Remote desktop video, H.264 / AV1, up to 4K at 60 fps
  • Keyboard and mouse (key repeat, shortcuts)
  • Opus audio
  • Terminal and background jobs
  • Files (resumable transfers)
  • Two-way clipboard sync
  • Port forwarding / VPN / mesh networking
  • Serial ports, USB, screenshots

Special networks and options

  • Connect by address: enter address:port, no server at all
  • Tailscale: preferred when both sides are on the same tailnet
  • NAT64: IPv6-only networks (such as Apple's app review network)
  • Refuse relays: remohop config relay off

Reliability

  • Survives short network drops; a broken session reconnects by itself
  • Host changes network or address: registered again within seconds
  • Works on small-MTU networks (starts at 1200 bytes)
  • A peer that vanishes is noticed within about 25 seconds

Four connection paths (chosen automatically; the fastest wins)

  1. ① LAN direct lan

    Same network, direct connection; the data never leaves the LAN

    set up in a few ms

  2. ② Hole punched punched

    Across networks, cone NATs, direct P2P

    set up in about 30–60 ms

  3. ③ Relay relayed (optional)

    Symmetric NATs, client isolation; forwards ciphertext only

    switches within about 1.5 s

  4. ④ Websocket bridge (optional)

    Networks that only reach the web (HTTPS on 443)

    tens of ms once remembered

Protocols and technology

  • UDP hole punching (low-TTL priming, simultaneous probes) + QUIC
  • TLS 1.3 encryption; CPace password authentication binds TLS to both identities
  • Pairing tokens: no password after pairing, revocable at any time
  • Access scopes (view only / control / files / allowed commands) + audit log
  • Hardware encoding: NVENC / QSV / AMF / VideoToolbox / VAAPI

How a connection is set up

  1. Register: the host registers with the rendezvous server using its Ed25519 identity, gets its 9-digit ID and keeps sending heartbeats.
  2. Start: the controller enters the ID (or an address:port directly, with no server).
  3. Exchange: the server sends both sides each other's candidate addresses (LAN / public / IPv6 / Tailscale) and NAT types.
  4. Punch: both send probes at the same time and the first path that answers wins (LAN first); with no path after 1.5 s, the relay is tried in parallel.
  5. Authenticate: CPace runs over QUIC (TLS 1.3); the password or pairing token never crosses the network. The host can ask for approval.
  6. Session: desktop, terminal, files and the rest are multiplexed over one encrypted session that reconnects after a drop.

NAT hole punching

Before
Device A NAT✕NAT Device B
After
Device A ⟵ direct QUIC · end-to-end encrypted ⟶ Device B
  • Both sides register with the rendezvous server, which sees each one's public address and port.
  • The server tells each side the other's candidate addresses, and both send UDP probes to each other at the same time.
  • Each outgoing probe opens a hole in its own NAT, so the other side's packets can come in.
  • Cone NATs can almost always be punched; when both sides are behind symmetric NATs, the relay is used automatically.

Key takeaways

  • The rendezvous server only handles registration, presence and punch coordination (and the optional relay); it never touches plaintext.
  • Once punched, data flows directly between the two devices, end-to-end encrypted.
  • No account needed, and you can skip the server entirely by connecting to an address.
  • One program: controller, host, server, web console and AI interface, all self-hostable.
  • The experience depends mostly on NAT type and network quality; if no direct path works, the relay takes over within 1.5 s.
