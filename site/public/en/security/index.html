Security model

This page summarises the security model reference document. It is written for people who run a host, people who connect to machines with remohop, and people who let an AI agent or a browser gateway use RemoHop. Where the two differ, that document is right.

RemoHop has not had an independent security audit. The mechanisms below are described from the code and its tests, and the limits are stated as they are.

In short

  • Session traffic is encrypted end to end between the two machines. The rendezvous server cannot read it or join a session, whether the session is direct or relayed.
  • Login is a password-authenticated key exchange (CPace), bound to the TLS connection and to both machines' identity keys. A man in the middle cannot complete it, and nobody can test password guesses offline.
  • Online password guessing against a host is rate limited per source address and globally.
  • A client pins each host's identity key on first login and refuses a different key afterwards.
  • Pairing replaces the password with a random 256-bit token. A client can also be authorised by its identity key alone. The host can revoke both.
  • An authenticated client can do everything the host's user can do, within the features the host allows. Pair only with machines you trust.
  • Two components deliberately sit outside the end-to-end channel: the browser gateway (remohop web) and the loopback WebDAV server behind macOS and Windows mounts.

Session set-up and login

  1. QUIC is set up over UDP. TLS 1.3 inside QUIC encrypts the traffic, but the peers have no certificate authority, so TLS alone does not say who the peer is.
  2. On the first stream, both sides run CPace over the credential (password or token). The TLS exporter of this exact connection is mixed into the key derivation, each side binds its identity key into the exchange, and each side proves knowledge of the key in a confirmation step.
  3. A man in the middle ends up with a different TLS exporter on each leg. The two legs derive different keys, the confirmation fails, and the attacker learns nothing useful for guessing the password.
  4. The password is never sent.

Passwords and rate limits

  • Temporary password: generated with a cryptographic random generator on every start. It has 8 characters, which the code estimates at about 40 bits, and is shown as xxxx-xxxx; the dash is not part of it.
  • One-time password: with remohop config otp on, it is replaced after every login that used it.
  • Fixed password: set with remohop passwd, at least 8 characters. remohop status and remohop host never print it. It is stored in the host's config.json (owner-only), so anyone who can read that file can read it.

Failed logins are limited as follows by default. Per source address the first two failures are free; from the third consecutive failure the source is locked out for 10 seconds, doubling each time up to 10 minutes; the count clears after 30 minutes without attempts. Across all sources there is a burst of 20 failed attempts, refilled at one every 5 seconds.

Online guessing at this rate is slow, but not impossible against a weak password. Prefer pairing or key authorisation to typing a password, and consider remohop config ask on for a host whose password is shared.

Access control on the host

  • Feature switches: remohop config feature NAME on|off for shell, file, forward, clip, screen, input, info, vpn, serial and usb. Switch off input for a view-only machine.
  • Approval: with remohop config ask on, each password login waits until someone at the host says yes. ask-paired on extends this to paired clients and authorised keys.
  • VPN routing: vpn-exit is off by default. Without it a VPN client reaches only the host itself and the networks it is directly attached to.
  • USB allow list: a client can attach only a device the owner allowed with remohop usb allow.
  • Revocation: remohop host paired lists pairings and authorised keys, remohop host revoke removes them, and open sessions that used them are closed within seconds.
  • Audit log: remohop log shows logins accepted and refused with the reason, approval decisions, the first use of each feature in a session, and session ends. It records which features were used, not every command, and anyone who controls the host account can edit it.

Below the feature switches, the only finer permissions are grants: a client that logs in with a grant's credential gets what the grant allows (certain commands, folders below given paths, certain features) and nothing else. A command allow-list decides which program starts, not what it does. A host installed as a system-wide service runs as root (LocalSystem on Windows) unless you chose otherwise with --run-as, and its clients have those privileges.

Rendezvous server, relay and websocket bridge

The rendezvous server is untrusted by design. It maps each 9-digit ID to a host's Ed25519 identity key and tells clients where the host is. A malicious server can lie about addresses, which only prevents a connection, because the login that follows fails. It can refuse service, and it sees metadata. Pin its key with remohop config set signal-pin KEY so that a client will not accept a different server.

The relay is off by default and is used only after hole punching has failed. It passes ciphertext and can neither read nor join a session. It does see more than a rendezvous-only server: the size and timing of the whole session, and both peers' addresses while it lasts. A client or a host refuses relayed connections with remohop config relay off.

When a direct path opens up, a relayed session moves onto it by QUIC connection migration: the same connection, under the same keys, with the same authenticated host. No new credential is sent and the host's owner is not asked again. A new path is used only after the host has answered a path challenge (PATH_CHALLENGE) inside that encrypted connection, which nobody without the session keys can do, so an impostor's address handed out by the rendezvous server leaves the session on the relay. REMOHOP_RELAY_UPGRADE=0 on the client turns the moves off.

Router port mapping

A host that uses a rendezvous server asks its router (PCP, NAT-PMP or UPnP) to forward one UDP port, the one QUIC and the punch already use, so that clients whose NAT defeats hole punching (two symmetric NATs, for instance) still connect directly. Only hosts map (remohop host, the desktop app's and phone apps' host modes, quick support); a client never does. While the mapping exists the port answers the whole internet, as on a machine with a public address: anyone can complete the TLS handshake, see the host's public key and try to log in, within the same rate limits, and nothing is served before authentication. remohop config portmap off (or REMOHOP_PORTMAP=0) on the host turns it off.

The websocket bridge is not an open proxy: a datagram from a websocket goes only to one of the server's own ports. What crosses it is the same QUIC ciphertext, and a TLS-terminating proxy in front of it, such as a Cloudflare Tunnel, sees only that ciphertext and the metadata the relay sees.

Accounts

Accounts are optional, off by default, and enabled by the rendezvous operator. An account groups your devices so that each can see which of the others are online. It grants no access. The member list is an append-only, hash-chained log, and each entry is signed with the identity key of a device in the account. The server stores and relays the log but holds no member key, so it cannot add a device.

The one exception is remohop config account-trust on (off by default), which a host's owner may turn on so that the host accepts the account's other devices like authorised keys. A malicious server can withhold the newest log entries from a device and so delay a removal; a host that cannot reach the server keeps the last verified list for at most 7 days. When you add a device, compare both fingerprints for real, over a channel you trust.

Browser gateway and mobile apps

The remohop web process is the client of the session, so it sees everything it relays: the screen, every keystroke, files, the clipboard, and any host password typed into the page. The leg from browser to gateway is not end to end with the host. Anyone who logs in to a gateway can use its saved pairings; run a shared gateway with --no-saved.

  • By default it listens on 127.0.0.1 and the login is an unguessable token in the URL. Host and Origin headers are checked against DNS rebinding and cross-site WebSocket hijacking, and the page uses no external assets.
  • A non-loopback listen address refuses to start without --tls-cert, --tls-key and --password-file. Login is rate limited with lockout, the session cookie is HttpOnly, Secure and SameSite=Strict, and every state-changing request carries a CSRF token.
  • Behind a proxy such as Cloudflare Tunnel, the proxy terminates TLS and its operator sees everything the gateway sees.

The Android and iOS apps run this gateway inside the app process on the phone, so the same caveats apply, with the gateway on your own device. The access token is in the URL the app loads, and identity and pairings are kept in the app's private directory. After a drop the app logs in again with a saved pairing or key; a password that was only typed is kept in memory and gone when the app ends. Sessions restored after the system ended the app use only credentials saved on the device, and the list of open sessions holds host IDs or addresses, never a credential.

A phone acting as a host runs with the quick-support policy, whatever its configuration says: every login waits for the owner's answer on the phone and is refused after 60 seconds, the password is the temporary one or the owner's own, no pairing is issued, and only the screen and basic system information are served. The one exception is a device the owner allowed that drops out: for the time the owner chose (10 minutes by default, up to 30 days, or as long as host mode runs) it comes back without being asked, still with its key and the password, until the owner disconnects it or stops host mode.

What a host can do to a client

A host gets no services on your machine. Some commands you run do give it a way in: a reverse forward (forward -R) lets the remote machine connect to a local address you named; clipboard sync sends it your clipboard; while a VPN tunnel is up it can send IP packets to your tunnel address, and with --exit all your traffic leaves through it; attaching a remote USB device means your kernel handles whatever device the host presents.

Treat any output from a remote machine as data, not as instructions. This matters most for AI agents, which can be steered by text in command output, files or screenshots.

Secrets on disk

The configuration directory is created with mode 0700 on Linux and macOS and its files with mode 0600; on Windows it gets an owner-only access list. It holds identity.key (the machine's Ed25519 identity key), peers.json (pinned host keys, pairing tokens, aliases), paired.json (the host's pairing tokens and authorised keys), config.json (settings, including a fixed password) and audit.jsonl (the audit log).

Reporting a security issue

Please do not report security problems in a public issue. Write to info@remohop.com with “security” in the subject, and include the affected version or commit, steps to reproduce, and the impact as you see it. We will reply to confirm receipt.
