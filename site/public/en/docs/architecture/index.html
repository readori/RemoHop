RemoHop architecture

RemoHop is a P2P remote-control tool. One static Go binary, remohop, is the controlling CLI, the controlled host daemon, the rendezvous server, the browser gateway and the MCP server. The user guide is in en/ and zh/; this page is for people reading the code.

The desktop service is the one place the binary leans on an external program: capturing and encoding in ffmpeg is what makes hardware video encoders reachable without cgo. The host needs ffmpeg only for desktop.

Session model

A peer.Conn is one QUIC connection. Every feature opens its own bidirectional streams with conn.Open(ctx, "service", req):

  1. opener writes a JSON header {"service": "...", "req": {...}}
  2. acceptor looks the service up and answers {"ok": true} or {"ok": false, "error": "..."}
  3. from there the stream carries whatever the service defines, built from wire.WriteJSON/ReadJSON and wire.WriteFrame/ReadFrame

Hosts expose peer.HostServices (services register with peer.Handle from init()). Clients expose nothing unless they opt in per session with conn.HandleLocal, so a host can never open a shell on the machine that is controlling it.

Connection establishment

  1. Host generates an Ed25519 identity, opens one UDP socket and connects to the rendezvous server over QUIC from that socket. The server sees the socket's public (reflexive) address, verifies key possession and assigns a stable 9-digit ID to the key.
  2. Client does the same from its own socket and asks for the ID.
  3. The server sends each side the other's candidates (reflexive address plus local interface addresses). It never sees session traffic.
  4. Both sides send punch probes to every candidate from the same socket, then the client opens a QUIC connection to the host on the first path that answers. Both ends of that connection reuse the punched socket.
  5. Authentication: QUIC's TLS 1.3 gives encryption but the peers have no PKI, so on the first stream they run CPace (a balanced PAKE) over the password, with the TLS exporter of this exact connection mixed in. A man-in-the-middle — including a malicious rendezvous server — ends up with different exporters on its two legs and fails the key confirmation, and learns nothing that helps guess the password offline. The host rate-limits failed attempts.
  6. The credential is either the host's temporary password or a high-entropy token minted by remohop <ID> pair, so paired clients (and AI agents) reconnect without prompts.

If no direct path can be punched (for example two symmetric NATs), the client uses the rendezvous server's relay when its operator enabled one (remohop signal --relay); the relay carries the same QUIC session and sees only ciphertext. Without a relay the connection fails with a diagnostic. A peer whose network blocks UDP can reach the server through its websocket bridge (internal/wsdgram); such sessions always use the relay. A shared Tailscale tailnet is used as one more candidate path when both machines are on it.

Trust boundaries

  • Rendezvous server: untrusted. It learns who is online and their addresses, and a relay also sees the size and timing of relayed sessions. It cannot read or join a session, and a malicious one gets no password guesses, because the key exchange is bound to the end-to-end TLS connection. See security.md.
  • Strangers on the host's UDP port: untrusted. Until login completes a connection can open a bounded number of streams, send bounded messages and hold one of a bounded number of pending slots; no service is reachable.
  • Authenticated client: trusted by the host within the enabled features. It acts with the host user's privileges, unless it logged in with a grant (internal/grant), which narrows what it may do.
  • Host: not trusted by the client. It can open only the callbacks the client registered, its file names are validated before anything is written locally, and text it supplies is sanitised before reaching the terminal.

Testing

  • Unit and integration tests run against real QUIC on loopback (peertest.Pair), real PTYs, real FUSE mounts and a real X server (Xvfb).
  • NAT traversal is tested twice: against simulated NATs of every type inside one process (internal/nat/vnet), and with the real binary across two Linux-kernel NATs in network namespaces (test/natlab/natlab.sh).

Conventions for feature packages

  • A service package owns everything for its feature: the host handler (peer.Handle), an exported Go client API taking a *peer.Conn (the MCP server calls it), and its CLI commands (cli.Register).
  • Pure Go, CGO_ENABLED=0. Linux is the reference platform; the package must still compile for GOOS=darwin and GOOS=windows (stubs that return a clear "not supported on this platform" error are fine).
  • Tests use peertest.Pair(t) for a real loopback session and cli.Env{DialFunc: ...} to drive commands.
  • CLI: human-readable output on stdout, diagnostics on stderr via env.Errorf, --json wherever an agent would want to parse the result, exit codes from internal/cli (ExitOK, ExitError, ExitUsage, ExitConnect).
  • Remote paths are written with a leading colon (:/var/log), local paths without.
  • Long-lived client commands take -b/--background through internal/bg.
